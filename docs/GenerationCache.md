# 生成缓存基础

三个用户生成节点（LLM 远程回复、API图像生成、API图片编辑）继承 `generation_cache.CachedGenerationNode`。该基类使 ComfyUI 每次执行都检查当前输入与来源配置；真正的复用由包内的会话缓存决定。`not_idempotent=True` 只影响 ComfyUI 的节点身份处理，不能替代这个检查。布尔条件返回与内部纠错请求不属于缓存生成节点，约定见下文。

## 新节点接入

1. 通过包的相对导入使用同一个 `generation_cache` 模块，并在 `__init__.py` 注册节点。不要用独立模块别名重复加载缓存。
2. 用 `input_key(node_type, inputs)` 计算键，`node_type` 使用稳定节点 ID。`inputs` 包含全部有效输入、解析后的接口地址和凭据；保留图片端口名、列表顺序和蒙版。不要只对 PNG 请求体或张量对象地址做哈希，也不要包含节点 ID、预览状态或强制刷新开关。
3. 文字调用 `CACHE.run(key, generate, force_refresh=...)`，得到 `(result, reused)`。`generate` 只在未命中或强制刷新时运行，返回不可变字符串、字节或由不可变值构成的元组。不得向缓存放入输入张量、显存张量或可被下游修改的对象。
4. 图片调用 `cached_image(key, generate, force_refresh=...)`，回调返回 PIL 图片。共用层保存无损 PNG 字节，每次返回独立 RGB 图片；在节点中转换为新的输出张量。
5. 预览、进度和输出格式由节点负责，命中缓存也要为本次执行恢复展示。执行列表沿用节点原有配对规则；编辑批次在完整输入哈希下按主图序号分别保存成功项。

`CACHE.run` 使用每个输入键独立的锁，同键并发请求合并，不同键仍可并行；等待时支持 ComfyUI 中断检查。回调异常或执行被中断时不会写入结果，也不会覆盖已有成功记录。强制刷新会等待同键正在执行的请求，然后重新生成。

## 生命周期与备份

缓存的“成功”指请求完成，不代表满足下游业务规则。LLM 的新增调度端口不计入请求输入哈希，也不写入全局缓存；旧工作流的首次回复缓存语义保持不变。

`CACHE` 是进程内共享实例，存活至 ComfyUI 退出，不设容量淘汰。缓存仅留哈希和不可变结果，不保留原始输入或明文 Key；内存随结果数量增长。新进程创建新的 `session_id`，图片编辑断点目录使用这个会话 ID 和同一个完整输入键隔离，不自动读取旧会话备份。

编辑节点的磁盘备份用于预览和本次启动中的缺失项续做；它们不是跨重启的自动缓存。预览目录被清理时从内存 PNG 恢复。新增磁盘恢复逻辑也必须限定当前 `CACHE.session_id`，避免绕过重启清空语义。

测试使用模拟服务，覆盖 A→B→A、多端口和蒙版变化、复制张量、输出被修改、并发同键去重、强制刷新失败、实际 ComfyUI 执行器和新进程启动。

## 布尔校验反馈重试

[布尔条件返回](../web/docs/LLMHarnessBooleanReturn.md) 用 GraphBuilder 复制参与校验的子流，内部 `LLMHarnessReplyRetry` 追加对话历史并重新请求。两个控制节点使用非稳定指纹，让执行器每次重新处理，内部纠错调用不继承 `CachedGenerationNode`，也不访问 `CACHE.run`。

- 首次回复仍可命中 LLM 缓存；连接调度时为当前节点重新构造上下文，必要时编码原始图片。
- 每次校验失败后的纠错请求始终调用模型，不复用相同错误的旧修正结果，也不替换首次请求的缓存；不同校验规则不会互相覆盖。
- 再次排队从首次回复和计数 0 开始，不续接上次失败的轮次。若初始缓存含不合格回复，它会再次校验，再使用本次预算纠错；可用“强制重新请求”替换初始回复。
- 调度对象保存连接名称、生成参数、编码后的 PNG 和对话历史，不携带 Key 或输入张量。它属于执行器数据，可能被执行器缓存暂留，不加入本包全局缓存，不保存到工作流或磁盘。
- 配置在每次纠错请求时重新读取。服务错误、超时和取消直接传播，不作为布尔 false 自动重试；没有跨进程恢复。

`tests/test_boolean_return.py` 验证上述语义，并确认真实执行器会等待最终通过后才放行下游。测试使用模拟服务。
