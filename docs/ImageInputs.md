# LLM 远程回复的图片输入

图片输入分为两组，均可不连接（只发送文本）：

- **图片1、图片2……**：原生自动增加输入口。多个口的图片在同一次请求中提交；每个口的 IMAGE 批次也会全部提交。普通口接执行列表时保持逐项执行。
- **列表合并图片**：将接入的整个执行列表合并到一次请求中，每项内部的 IMAGE 批次也全部提交。不同尺寸的图片逐张编码，不拼接、不补齐画布。这里的“合并”指同一次请求携带多张独立图片。

例如，`切分预览（自动切块）` 切出 5 块，接到 **列表合并图片**，在提示词等其他输入为单值时会发出 **1 次请求，携带 5 张图片**。接到普通图片口则发出 5 次请求。

每次请求按普通图片口的编号、各口的批次顺序、合并列表顺序及其内部批次顺序发送。普通图片口、提示词或其他设置若带执行列表，按最长列表逐项运行，较短列表复用末项；合并口的全部图片会随每次请求一起发送。回复按请求顺序输出，下游仍逐项处理。

原生自动增长输入最多提供 100 个图片口；单个批次及合并列表不受这个端口数量限制。图片按输入宽高编码为 PNG，不在本地缩放。“图片最长边”设置已移除，旧 API 中残留的该字段会被忽略。服务端自行缩放或拒绝超限输入，不在本地预先限制尺寸。

“超时（秒）”传给 `urllib.request.urlopen(timeout=...)`，用于网络连接及阻塞读写等待，不是首个 token 的专用超时，也不是整个请求的总时限。流式接收期间仍有效，心跳等网络数据也可能让等待继续；持续收到数据时，总耗时可以超过所设秒数。本地图片编码不计入这个网络超时。

旧画布加载时会自动保留并转换图片1～3的接线；旧 API 工作流的 `image_1`、`image_2`、`image_3` 也继续可用。新 API 使用 `images.图片1`、`images.图片2`……和 `image_list`。文本及连接配置字段不变。
