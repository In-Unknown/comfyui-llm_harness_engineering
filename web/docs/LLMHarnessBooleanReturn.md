# 布尔条件返回

把 LLM 回复交给下游校验，再决定放行、携带错误重试，或报错停止当前工作流。适合要求 JSON 格式、字段类型、数值范围等必须满足条件的生成任务。

节点 ID：`LLMHarnessBooleanReturn`；分类：`llm_harness`。本节点负责反馈调度，不自行解析 JSON 或判断数值；实际规则由产生布尔值的校验节点决定。

## 第一次使用 / 配置来源

先在 [LLM 远程回复](llm_remote_reply.md) 配置连接和模型。本节点没有独立服务配置，重试沿用首次请求的连接名称、模型、原始提示词、系统提示词、图片和生成参数。API Key 仍从本地 `data/connections.json` 读取，不保存到工作流。

将 LLM 的 `调度` **直接**连接到本节点的 `调度输入`，将 `回复文本` 连接校验子流。校验子流的布尔结果接 `校验通过`，错误文本接 `报错信息`。报错信息默认是多行文本控件，需要动态错误时将其转换为输入。

## 参数和输出

### 输入

| 参数 | 描述 | 数据类型 | 必需 |
| --- | --- | --- | --- |
| `调度输入` | 直接连接对应 LLM 的 `调度`；包含本轮回复、原始请求上下文和已用重试历史。不支持中间处理后再接入或交叉配对 | LLM_HARNESS_SCHEDULE | 是 |
| `校验通过` | 校验子流输出的单个真实布尔值；`true` 放行，`false` 重试或报错。没有默认值，必须连接 | BOOLEAN | 是 |
| `最大重试次数` | 默认 `3`；首次回复之后最多追加的请求数，必须是非负整数。`0` 表示第一次失败立即报错；首次进入本节点后固定本次预算 | INT | 是 |
| `报错信息` | 默认 `回复未满足要求，请检查格式或数值范围。`；可填写固定说明或连接本轮动态错误。重试时在该文本前后自动添加固定反馈语句，组成 user 消息发给模型，详见下方“自动添加的错误反馈”；次数耗尽时放入工作流异常。全空白使用 `回复未通过校验。` | STRING | 是 |

四个输入每轮都必须恰好有一项。控件默认值可以满足必需输入，不代表该输入可缺失。字符串 `"false"`、数字 `0` 不能代替布尔 `false`。

### 输出

| 输出名称 | 描述 | 数据类型 |
| --- | --- | --- |
| `回复` | 最终通过校验的完整回复文本，单个字符串；等待全部重试结束才向下游输出，不输出失败轮次 | STRING |
| `重试次数` | 本次最终通过时已追加的模型请求次数；首次通过为 `0`，重试一次通过为 `1`。单个整数 | INT |

失败且次数耗尽时抛出异常，没有正常输出。输出的是回复文本，不是校验节点解析出的数组或对象；需要结构化结果时，把本节点的 `回复` 再接解析节点。

## 示例：生成并校验 JSON 记录数组

下面使用 `comfyui-liuxinyu-packs` 中的 **解析并校验 JSON 记录数组**（`LiuxinyuParseJSONRecords`）。其他能输出 BOOLEAN 和 STRING 的校验节点也可替换它；harness 包本身不依赖该包。

1. LLM 系统提示词填 `只返回符合要求的 JSON，不附带解释。`，提示词填 `生成一条任务记录，顶层为数组，字段 id 为非空字符串、count 为整数，例如 [{"id":"A","count":2}]。不要增加其他字段。`。
2. 校验节点的 `必需字段与类型` 填 `{"id":"nonempty_string","count":"integer"}`，关闭 `允许其他字段`。
3. 添加“布尔条件返回”，`最大重试次数` 填 `2`，将 `报错信息` 转换为输入，按下表连线。

| 来源节点与输出 | 目标节点与输入 |
| --- | --- |
| LLM 远程回复 → `调度` | 布尔条件返回 → `调度输入` |
| LLM 远程回复 → `回复文本` | 校验节点 → `输入文本` |
| 校验节点 → `校验通过` | 布尔条件返回 → `校验通过` |
| 校验节点 → `错误信息` | 布尔条件返回 → `报错信息` |
| 布尔条件返回 → `回复` | 后续文本处理，或另一个 JSON 解析节点的文本输入 |

4. 运行工作流。例如首次得到 `[{"id":"A","count":"2"}]`，校验返回 `false` 和字段类型错误；节点将这份回复和错误发回模型，重新请求并重跑校验。
5. 若下一次得到 `[{"id":"A","count":2}]`，校验通过，下游收到这份文本，`重试次数` 为 `1`。若三次回复都失败（首次 + 两次重试），工作流报错停止。

**不要把前置校验节点的数组直接接到最终处理分支。** 它可能在首次校验时输出空数组或旧结果。需要最终数组时，在“布尔条件返回”之后再添加解析节点，使用已通过校验的回复文本解析。

该示例校验器允许空记录数组，也不检查数值范围或记录数量。若要求 `count` 在 1～10 内、数组非空等，必须由相应校验子流检查，不能只在提示词里说明却把字段类型检查当作范围检查。

## 数值范围和多项规则

例如要求 `{"value":5}` 中的 `value` 是 0～10 的整数，校验子流应先安全解析 JSON，再检查字段存在、整数类型和范围；把所有规则合并成**一个**布尔结果，并提供本轮错误文本。

| 本轮回复 | 校验通过 | 报错信息示例 |
| --- | --- | --- |
| `{"value":5}` | `true` | 空字符串 |
| `{"value":50}` | `false` | `value 必须为 0 到 10 的整数，实际为 50` |
| `{"value":"5"}` | `false` | `value 必须是整数，不能是字符串` |
| `这次返回 5` | `false` | `回复不是合法 JSON 对象，请只返回 {"value":整数}` |

解析失败需要转成 `false` 和错误文本。直接抛异常的解析器不能作为可重试校验的第一步，否则尚未执行本节点就已经停止。程序异常、服务错误和用户取消不作为校验失败自动重试。

## 重试次数与上下文

| 最大重试次数 | 最多模型请求次数（首次未命中缓存时） | 失败行为 |
| --- | --- | --- |
| `0` | 1 | 首次校验失败立即停止 |
| `1` | 2 | 允许一次修正，仍失败则停止 |
| `3`（默认） | 4 | 允许三次修正，仍失败则停止 |

每次重试保持原始用户提示词及图片、系统提示词和生成参数，并按时间顺序追加每次失败的 **assistant 回复 + user 错误反馈**。第二次重试包含第一次错误和第二次错误，不只保留最后一条，不重复拼接系统提示词。校验通过当轮不会再请求。

本节点依据用户连接的布尔结果执行控制，不启用接口的 JSON Schema 强制输出协议。重试可能产生服务费用，上下文会随轮次增长，服务端上下文限制仍适用。连接配置每次请求读取，运行期间不应修改正在使用的来源。

## 自动添加的错误反馈

`报错信息` 输入提供的是具体错误内容。校验失败且仍有重试次数时，节点会自动在其前后添加固定文字，发送给模型的完整反馈为：

```text
上一次回复未通过校验，错误信息：
〈报错信息输入的原文〉
请结合原始要求和以上对话重新生成完整回复，修正这些错误。
```

这里的 `〈报错信息输入的原文〉` 会被实际错误替换，不会作为占位符发出。例如上面的 count 类型错误会形成：

```text
上一次回复未通过校验，错误信息：
第 1 项的 'count' 必须是 integer。位置 $[0]["count"]；实际为 string，值为 "2"。
请结合原始要求和以上对话重新生成完整回复，修正这些错误。
```

前后的两句由代码自动添加，不来自任何节点输入，也不需要用户在 `报错信息` 中重复填写。当前没有用于修改这两句的节点参数。全空白错误先替换为 `回复未通过校验。`，再添加上述文字；其他非空白错误原样嵌入，不自动补充字段位置、重复值或修复方案。

代码入口是包根目录 `llm_remote_reply.py` 的 `_retry_feedback(error)`，三种 API 格式共用这段反馈。`false` 只控制是否重试，不会被额外发送为一条模型消息。校验通过时直接输出回复；次数耗尽时在本地报错，两种情况都不会再发送这条反馈。

## 单次重试请求的完整内容

每次重试都是一次新的 API 请求，在这一次请求内携带完整累计对话。第一次重试的消息顺序是：

| 顺序 | 身份 | 内容 |
| --- | --- | --- |
| 1 | system / 系统指令 | 初次请求的完整系统提示词；为空时不发送 |
| 2 | user | 初次请求的全部图片（如有）及完整用户提示词 |
| 3 | assistant | 刚刚未通过校验的完整模型回复 |
| 4 | user | 具体错误加上前后固定文字，组成上一节展示的完整反馈 |

### 第一次失败后的完整请求体示例

沿用上面的任务记录示例，假设首次回复为 `[{"id":"A","count":"2"}]`，校验发现 count 是字符串。以下展示 **Chat Completions** 的完整 JSON 请求体（不包含 URL 和认证请求头）：

```json
{
  "model": "example-model",
  "messages": [
    {
      "role": "system",
      "content": "只返回符合要求的 JSON，不附带解释。"
    },
    {
      "role": "user",
      "content": [
        {
          "type": "text",
          "text": "生成一条任务记录，顶层为数组，字段 id 为非空字符串、count 为整数，例如 [{\"id\":\"A\",\"count\":2}]。不要增加其他字段。"
        }
      ]
    },
    {
      "role": "assistant",
      "content": "[{\"id\":\"A\",\"count\":\"2\"}]"
    },
    {
      "role": "user",
      "content": "上一次回复未通过校验，错误信息：\n第 1 项的 'count' 必须是 integer。位置 $[0][\"count\"]；实际为 string，值为 \"2\"。\n请结合原始要求和以上对话重新生成完整回复，修正这些错误。"
    }
  ],
  "temperature": 0.2,
  "max_tokens": 1024,
  "stream": true
}
```

`example-model` 是示例模型名；温度 0.2、最大输出长度 1024 是本例假定的初次请求参数，不是返回节点的固定设置。实际请求沿用上游模型与参数。本例没有图片，思考强度关闭；若启用思考强度，Chat Completions 请求还带 `reasoning_effort`。JSON 中的 `\n` 表示换行，`\"` 表示字符串内部的引号。

若初次请求有图片，它们会在第二条 user 消息中按原顺序放在文本之前：Chat Completions 使用 `image_url` 内容块，图片内容为 `data:image/png;base64,...`。每次重试保留这些原图，不把图片转成说明文字，也不只发送错误反馈。

### 第二次及后续重试

如果修正后的回复仍然失败，下一次请求会保留上例所有消息，再追加“新的完整 assistant 回复”和“新的完整 user 错误反馈”。例如第二次回复遗漏 count，第二次重试中的消息按下列顺序发送：

```text
system：原始系统提示词
user：原始图片（如有）和原始提示词
assistant：[{"id":"A","count":"2"}]
user：上一次回复未通过校验，错误信息：
第 1 项的 'count' 必须是 integer。位置 $[0]["count"]；实际为 string，值为 "2"。
请结合原始要求和以上对话重新生成完整回复，修正这些错误。
assistant：[{"id":"A"}]
user：上一次回复未通过校验，错误信息：
第 1 项字段不符合契约；缺少 ['count']，额外 []。位置 $[0]。
请结合原始要求和以上对话重新生成完整回复，修正这些错误。
```

上面的每个身份标记代表一条独立消息；实际通过接口的角色字段区分，不把 `assistant：` 等标签拼进原始提示词。所有失败回复保留全文，按时间顺序逐对追加，不只保留最近一轮，也不由服务端会话 ID 自动补全历史。用户提示词及图片在每次请求中保留一份，系统提示词也保留一份。

### 三种 API 格式的对应关系

三种接口发送的原始上下文、失败回复和反馈文字一致，区别在请求字段：

| API 格式 | 系统提示词 | 原始输入与累计历史 |
| --- | --- | --- |
| Chat Completions | `messages` 中首条 `system` 消息 | 原始 user 消息后，逐对追加 assistant 回复和 user 反馈 |
| Responses | 请求顶层 `instructions` | `input` 中原始 user 的 `input_image` / `input_text` 后，追加 assistant 的 `output_text` 和 user 的 `input_text` |
| Anthropic Messages | 请求顶层 `system` | `messages` 中原始 user 的 image / text 内容块后，逐对追加 assistant 回复和 user 反馈 |

系统提示词为空时省略对应消息或字段。错误反馈始终作为 user 消息发送，不改写系统提示词。新回复回来后再执行同一校验子流；通过后输出的是新回复本身，不包含固定反馈文字或整段对话历史。

## 校验子流和下游执行边界

重试时只复制 LLM 到本节点之间、依赖本轮回复且参与本节点输入的校验节点；独立上游参数保持原引用。新回复重新进入校验子流，动态错误信息随之更新。不要在校验子流中保存文件、提交外部任务等，因为这些操作会随重试重复。

后续工作必须依赖本节点输出。直接接 LLM 原始回复、前置校验结果，或完全独立的旁路，不会被本节点自动拦截；抛错也不能撤销已经完成的旁路操作。本节点是执行终点，即使输出未接其他节点也会参与正常排队，能够触发校验和报错。

调度线必须直接配对。校验子流内部暂不支持嵌套循环边界；可在外层循环中逐次完成回复校验。

## 执行列表与图片批次

本节点每轮只接受一条回复。若 LLM 的提示词或普通图片口产生多项执行列表，请先在外层分包，让每次请求输入为单项；不要把多个调度值或布尔值直接接入。错误会在执行到本节点时报告，之前的初始请求可能已经发出。

单个 IMAGE 批次和 `列表合并图片` 携带多张图片仍可使用，只要生成一条回复。重试保留首次请求的 PNG 图片内容和顺序，不重新执行原始图片生成节点。详见 [图片输入](../../docs/ImageInputs.md)。

## 缓存、重跑与超时

首次回复沿用 LLM 会话缓存；**错误反馈后的重试始终调用服务，不读取或写入普通回复缓存**。修正结果不覆盖原始提示词的缓存，避免一种校验规则影响其他工作流。再次排队从首次回复和计数 `0` 开始，可能先命中此前未通过本规则的回复，再重新校验和修正。首次请求也要重新生成时，开启 LLM 的 `强制重新请求`。

重试上下文属于 ComfyUI 执行数据，保留编码图片和对话，不保留输入 GPU 张量，不加入包的全局生成缓存或工作流文件。执行器缓存可能在运行后暂留这些数据，但不支持跨重启恢复。重启后历史、计数及会话缓存清空。

超时沿用 LLM 的 `超时（秒）`，作用于每次请求的网络连接和阻塞读写，不是整个重试循环的总时间。HTTP 错误、超时、流中断或用户取消直接传播，不用剩余预算继续请求。发生服务错误后再次排队从初始请求流程开始，没有断点续作。

## 常见问题

| 现象 | 检查方法 |
| --- | --- |
| 一直重试直到报错 | 确认布尔值来自当前回复，未固定为 false；检查规则可满足，错误文本说明了具体原因 |
| 第一次错误就停止 | 检查上限是否为 0；检查错误是否来自校验器自身、HTTP 或超时 |
| 下游用了旧回复 | 下游应连接本节点的 `回复`，不要连接 LLM 原输出或前置解析结果 |
| 多项执行列表报错 | 先分包；一个图片批次与多个执行项不是同一概念 |
| 调度配对报错 | 直接连接同一个 LLM 的调度口，校验文本也应来自该 LLM |
| 原 LLM 面板显示多轮文本 | 重试复用原节点显示位置，面板追加各轮流式文本；最终结果以本节点输出为准 |

## 开发与验证

根 `__init__.py` 接入 `boolean_return.NODE_CLASSES`。`LLMHarnessReplyRetry` 是子图展开使用的内部节点，默认不在添加菜单展示，不是额外的用户操作步骤。原 LLM 的回复端口仍为索引 `0`，新增调度为索引 `1`。

`tests/test_boolean_return.py` 使用模拟接口和实际 ComfyUI 执行器验证重试、上下文、次数、失败及下游等待，不发起付费请求。更新后需重启后端并刷新页面，旧实例不会自动加载 Python 改动。
